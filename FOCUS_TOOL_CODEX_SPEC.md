# Focus Tool — подробная инструкция для Codex

> Цель: создать полностью рабочий локальный веб‑сайт **Focus Tool** — удобный to‑do list + focus timer + календарь + дневной профиль + мягкая геймификация. Это не макет и не статическая витрина: все ключевые сценарии должны реально работать, сохраняться между перезагрузками и быть приятными в ежедневном использовании.

---

## 1. Главная задача

Создай одностраничное веб‑приложение **Focus Tool** для персональной продуктивности. Приложение должно ощущаться как качественный **90s Magical Girl Digital Organizer**, переосмысленный для современного браузера: pastel-pink electronic diary, cream LCD-панели, мягкие рамки, аккуратные magical-girl детали, плавные анимации, понятная визуальная иерархия и удобные controls. Это должен быть функциональный productivity tool, а не просто декоративный mockup.

Продукт объединяет пять основных частей:

1. **Today / Dashboard** — обзор текущего дня.
2. **To‑Do List** — быстрый и удобный список задач.
3. **Focus Tool** — таймер фокус‑сессий с привязкой к задачам.
4. **Calendar** — планирование задач по датам.
5. **Profile / Daily Check‑in** — имя, настроение дня, заметка «О чём я сегодня думаю».

Дополнительно:

- начисление очков за выполненные задачи;
- начисление очков за завершённые focus‑сессии;
- дневной трекер эффективности;
- поздравление после выполнения любых трёх задач за день;
- 30 заранее подготовленных поощрительных сообщений, выбираемых случайно;
- demo‑кнопка **«Сбросить»**;
- всё пользовательское состояние хранится **только локально в `localStorage`**;
- никакого backend, базы данных, авторизации и облачной синхронизации в этой версии не требуется.

---

## 2. Непереговорные требования

Следующие пункты обязательны и не должны быть заменены заглушками:

- React + TypeScript + Vite.
- Полностью рабочее приложение, а не UI‑демо.
- `localStorage` для состояния.
- Реальное сохранение задач, профиля, настроения, дневной заметки, focus‑сессий, очков и статистики.
- Сегодняшняя дата.
- Текущее локальное время **с секундами**, обновляющееся каждую секунду.
- To‑Do List.
- Calendar.
- Focus Tool.
- Profile window.
- Daily efficiency tracker.
- Gamification / points.
- Случайное поздравление при достижении 3 выполненных задач за день.
- Кнопка «Сбросить» для demo‑режима.
- Плавные, но не навязчивые анимации.
- Понятные иконки у важных действий.
- Полная адаптивность как минимум для desktop, tablet и mobile.
- Интерфейс не должен разваливаться при длинных названиях задач или заметках.
- Никаких ошибок в console.
- Production build должен проходить успешно.

# 3. Референс дизайна и работа с asset sheet

Визуальный референс уже определён: **90s Magical Girl Digital Organizer / kawaii electronic planner**.

Это ключевое направление проекта. Сайт должен выглядеть не как generic productivity SaaS, а как красивый персональный электронный органайзер из конца 90-х / начала 2000-х, переосмысленный как современное веб-приложение.

Главная визуальная формула:

> **pastel magical-girl organizer + retro digital device + modern UX**

Нельзя превращать интерфейс в детскую игрушку или декоративную картинку, в которой неудобно работать. Все игровые и kawaii-элементы должны поддерживать атмосферу, а основной UX остаётся быстрым, понятным и функциональным.

## 3.1. Что конкретно брать из референса

Обязательно перенести следующие визуальные принципы:

- очень светлый пастельно-розовый основной фон;
- кремовые / ivory внутренние панели;
- нежно-розовые, персиковые и лиловые акценты;
- тонкие контурные рамки вокруг карточек;
- ощущение округлого пластикового корпуса электронного органайзера;
- крупные мягкие радиусы, но не современный «glassmorphism»;
- небольшие внутренние тени и мягкие внешние тени;
- визуальные слои, похожие на отдельные физические панели устройства;
- маленькие декоративные звёздочки, искры, луны, огоньки, сердечки, крылышки и magical-girl символика;
- отдельные цветные pill-кнопки;
- центральный круглый/овальный Focus Timer как главный визуальный объект;
- цифровое отображение времени;
- мини-календарь;
- компактная панель профиля / аватара;
- небольшие status / reward panels;
- pastel UI с низкой визуальной агрессией;
- лёгкая ретро-электронная эстетика без настоящего pixel-art интерфейса.

Важное правило: **не копировать надписи, цифры, чужие иллюстрации или конкретные данные с референса**. Использовать композиционный и визуальный язык, но наполнить его функциями Focus Tool.

## 3.2. Композиция страницы должна быть близка по ощущению к референсу

На desktop интерфейс должен восприниматься как **единый большой электронный органайзер**, внутри которого расположены отдельные панели.

Предпочтительная композиция:

```text
┌─────────────────────────────────────────────────────────────────┐
│ Brand / Focus Tool     Live date + clock       score + avatar   │
├───────────────────┬────────────────────────┬────────────────────┤
│                   │                        │ Today / Profile     │
│ TO-DO LIST        │      FOCUS TOOL        │ mood + thought     │
│                   │                        ├────────────────────┤
│ today's tasks     │   large round timer    │                    │
│ upcoming          │                        │ mini calendar      │
│ completed         │ presets + controls     │                    │
│                   │                        │                    │
├───────────────────┴────────────────────────┼────────────────────┤
│ Daily / weekly efficiency + stats          │ achievement card   │
├────────────────────────────────────────────┴────────────────────┤
│ optional Archive / settings / Demo Reset                        │
└─────────────────────────────────────────────────────────────────┘
```

Это не означает обязательную pixel-perfect сетку. Сохрани **визуальный баланс референса**: большая центральная focus-зона, функциональная левая колонка, компактная правая колонка и нижний блок статистики.

## 3.3. Не делать обычный sidebar-dashboard

Для этого проекта **не использовать по умолчанию классическую SaaS-схему с тёмным/серым sidebar слева**.

Desktop-версия должна ощущаться как один цельный digital organizer. Навигация может быть встроена в:

- верхнюю панель;
- небольшие tabs;
- bottom utility controls;
- отдельные compact buttons.

Если все основные функции помещаются на dashboard, Today / To-Do / Focus / Calendar / Profile должны работать прежде всего как взаимосвязанные панели одного рабочего экрана, а не как пять изолированных страниц.

## 3.4. Asset sheet имеет высокий приоритет

Пользователь дополнительно загрузит asset sheet / asset list. Когда он появится в проекте:

1. сначала внимательно изучить его;
2. определить все самостоятельные визуальные элементы;
3. сопоставить элементы с референсом и UI;
4. только затем финализировать оформление компонентов.

Пользовательские ассеты имеют приоритет над случайными emoji, clip-art и самодельными декоративными заменами.

Для текущей версии проекта считать загруженный reference sheet главным источником визуального языка. Использовать его как опорный reference при сборке сайта и при создании новых ассетов, когда прямое извлечение из листа невозможно или даёт плохой результат.

## 3.5. Composite asset sheet нельзя использовать целиком

Если пользователь загрузил один большой лист с несколькими объектами/иллюстрациями, **запрещено** вставлять этот sheet целиком как одну картинку в интерфейс.

Для этого проекта считать основным reference именно загруженный пользователем **asset/reference sheet**. Его нужно использовать как главный визуальный ориентир для формы объектов, палитры, толщины контуров, типа бликов, декоративных мотивов и общего характера magical-girl UI.

Нужно:

1. определить все самостоятельные визуальные элементы;
2. попытаться аккуратно разрезать sheet на отдельные ассеты;
3. экспортировать их в отдельные файлы;
4. сохранить прозрачность, если она есть;
5. убрать лишние поля вокруг объектов;
6. дать понятные имена;
7. положить их в структурированную папку `src/assets/` или существующую папку assets проекта;
8. подключать уже отдельные файлы в соответствующих компонентах.

### 3.5.1. Если вырезается плохо — не тащить кривой crop в прод

Если какой-то элемент из reference sheet:

- обрезается неровно;
- теряет часть формы;
- имеет рваные края;
- содержит лишний фон/мусор;
- слишком слеплен с соседними объектами;
- после вырезания выглядит хуже, чем весь остальной интерфейс,

то **не использовать такой плохой crop**. Вместо этого нужно **самостоятельно сгенерировать или перерисовать аналогичный ассет с нуля**, но строго в стиле reference sheet.

То есть логика такая:

1. сначала попробовать извлечь оригинальный элемент из sheet;
2. если extraction качественный — использовать extracted asset;
3. если extraction некачественный — создать новый matching asset с нуля;
4. новый ассет должен визуально совпадать по стилю с reference sheet и не выбиваться из общего набора.

Нельзя оставлять в проекте компромиссные ассеты формата «вроде вырезалось, и так сойдёт». В приоритете всегда **чистый, целый, аккуратный итоговый файл**, даже если для этого пришлось пересоздать элемент.

### 3.5.2. Что сохранять при самостоятельной генерации ассета

Если какой-то элемент приходится генерировать заново, обязательно сохранить:

- ту же pastel magical-girl палитру;
- мягкие розово-золотые или лилово-персиковые контуры;
- глянцевые блики;
- округлые формы;
- тот же уровень детализации;
- kawaii/retro-electronic настроение;
- схожий визуальный вес и масштаб относительно других ассетов.

Нельзя генерировать ассет в чужом стиле, в плоском generic-vector стиле или в несочетающемся semi-realistic стиле.

Пример структуры:

```text
src/assets/
  brand/
  focus/
  calendar/
  profile/
  rewards/
  decorations/
  icons-custom/
```

Имена файлов должны быть смысловыми, например:

```text
focus-star.png
focus-flame-left.png
focus-flame-right.png
reward-perfect-day.png
profile-avatar-frame.png
calendar-sparkle.png
panel-corner-decoration.png
```

Если sheet возможно нарезать скриптом без потери качества — создай вспомогательный script в `scripts/` и выполни нарезку программно.

Если фон листа однотонный, удалять его можно только тогда, когда это делается чисто и не повреждает края иллюстраций.

Не генерируй произвольные замены пользовательским ассетам, если нужный элемент уже присутствует на asset sheet.

## 3.6. Создать manifest ассетов

После подготовки изображений создай единый manifest, например:

```ts
export const assets = {
  brand: {
    logo: focusToolLogo,
  },
  focus: {
    star: focusStar,
    flameLeft: focusFlameLeft,
    flameRight: focusFlameRight,
  },
  rewards: {
    perfectDay: rewardPerfectDay,
  },
};
```

Не разбрасывай строковые пути к картинкам по компонентам.

## 3.7. Оптимизация ассетов

- использовать WebP/PNG/SVG в зависимости от исходника;
- не ухудшать качество исходных иллюстраций;
- не апскейлить маленький raster через CSS до огромных размеров;
- обязательно задавать `width`/`height` или `aspect-ratio`, чтобы интерфейс не прыгал;
- декоративные изображения должны иметь `pointer-events: none`;
- изображения, не несущие смысла, скрывать от screen reader через пустой `alt`;
- не хранить декоративные изображения в `localStorage`;
- не использовать один и тот же крупный декор десятки раз, если это создаёт визуальный шум.

# 5. Архитектурный принцип

UI не должен напрямую читать и писать `localStorage` из каждого компонента.

Сделай слой состояния и слой repository/storage.

Пример:

```text
UI component
   ↓
application/state action
   ↓
localProgressRepository
   ↓
localStorage
```

Все изменения данных проходят через единые функции.

Это необходимо для:

- предсказуемого начисления очков;
- корректного reset;
- миграций схемы;
- предотвращения дублирования наград;
- тестируемости.

# 6. localStorage

## 6.1. Namespace

Использовать один основной ключ:

```text
focus-tool:v1
```

Не очищать весь `localStorage` браузера.

Кнопка reset должна удалить только данные Focus Tool.

## 6.2. Версионирование

State обязательно содержит:

```ts
schemaVersion: 1
```

При будущих изменениях предусмотреть миграции.

## 6.3. Safe parse

Чтение делать через `try/catch`.

Если JSON повреждён:

- приложение не падает;
- записывается warning в console;
- используется дефолтное состояние;
- повреждённая запись может быть сохранена в backup key перед восстановлением.

Запись также оборачивать в `try/catch` и корректно обрабатывать `QuotaExceededError`.

## 6.4. Не хранить ассеты в localStorage

В `localStorage` храним только JSON‑состояние приложения.

Изображения остаются обычными static assets.

## 6.5. Локальная дата

Для дневной статистики использовать локальную календарную дату пользователя в формате:

```text
YYYY-MM-DD
```

Не определять «сегодня» через голый `toISOString()`, потому что UTC может дать соседний день.

Создать utility типа:

```ts
getLocalDateKey(date: Date): string
```

# 7. Предлагаемая модель данных

Примерная схема. Можно улучшить названия, но смысл должен сохраниться.

```ts
type Priority = 'low' | 'medium' | 'high';
type TaskStatus = 'active' | 'completed';
type FocusMode = 'focus' | 'shortBreak' | 'longBreak';
type TimerStatus = 'idle' | 'running' | 'paused';

type Mood = 'great' | 'good' | 'neutral' | 'tired' | 'low';

interface Task {
  id: string;
  title: string;
  description?: string;
  status: TaskStatus;
  priority: Priority;
  scheduledDate?: string;       // local YYYY-MM-DD
  scheduledTime?: string;       // HH:mm
  estimatedMinutes?: number;
  createdAt: number;
  updatedAt: number;
  completedAt?: number;
  order: number;
  rewardedCompletionId?: string;
}

interface DailyCheckIn {
  date: string;
  mood?: Mood;
  thought: string;
  updatedAt: number;
}

interface FocusSession {
  id: string;
  taskId?: string;
  mode: 'focus';
  plannedMinutes: number;
  startedAt: number;
  completedAt: number;
  pointsAwarded: number;
}

interface ActiveTimer {
  mode: FocusMode;
  status: TimerStatus;
  taskId?: string;
  plannedSeconds: number;
  remainingSeconds: number;
  startedAt?: number;
  endsAt?: number;
  pausedAt?: number;
}

interface PointEvent {
  id: string;
  type: 'task_completed' | 'focus_completed';
  points: number;
  createdAt: number;
  localDate: string;
  entityId: string;
}

interface DailyMilestones {
  [date: string]: {
    threeTasksCelebrated?: boolean;
  };
}

interface FocusSettings {
  focusMinutes: number;
  shortBreakMinutes: number;
  longBreakMinutes: number;
  sessionsBeforeLongBreak: number;
  dailyFocusGoalMinutes: number;
  soundEnabled: boolean;
}

interface UserProfile {
  name: string;
}

interface FocusToolState {
  schemaVersion: 1;
  profile: UserProfile;
  checkIns: Record<string, DailyCheckIn>;
  tasks: Task[];
  focusSessions: FocusSession[];
  pointEvents: PointEvent[];
  milestones: DailyMilestones;
  activeTimer: ActiveTimer;
  focusSettings: FocusSettings;
  completedFocusCountSinceLongBreak: number;
}
```

Для ID использовать `crypto.randomUUID()` с fallback при необходимости.

# 8. Основной layout

## 8.1. Desktop — единый magical digital organizer

На desktop **не строить обычную административную панель**. Основной экран должен выглядеть как цельный пастельный электронный органайзер, разделённый на функциональные секции.

Рекомендуемая сетка при ширине примерно 1200–1600 px:

```text
┌────────────────────────────────────────────────────────────────────┐
│ Logo / Focus Tool        Date + HH:MM:SS        points + profile   │
├────────────────────┬─────────────────────────┬─────────────────────┤
│ TO-DO              │                         │ TODAY               │
│                    │       FOCUS TIMER       │ mood                │
│ task groups        │                         │ daily thought       │
│ quick add          │       main circle       ├─────────────────────┤
│ priorities         │                         │ CALENDAR            │
│ completion         │ presets / start/pause   │ compact month       │
├────────────────────┴─────────────────────────┼─────────────────────┤
│ DAILY EFFICIENCY / STATS                     │ REWARD / STREAK     │
├──────────────────────────────────────────────┴─────────────────────┤
│ Archive / secondary actions / Demo Reset                           │
└────────────────────────────────────────────────────────────────────┘
```

Примерные пропорции:

- левая колонка: `32–36%`;
- центральная focus-зона: `34–38%`;
- правая колонка: `26–30%`.

Это ориентир, а не жёсткая математика.

Ключевой элемент — **Focus Timer визуально находится в центре и немного доминирует**, как в референсе.

To‑Do List при этом должен оставаться достаточно широким для реальной работы. Если задач много, список получает внутренний scroll, а не растягивает весь интерфейс бесконечно вниз.

## 8.2. Верхняя панель

Верхняя панель должна состоять из трёх визуальных капсул / панелей:

1. бренд **FOCUS TOOL** с декоративной звездой или пользовательским brand asset;
2. сегодняшняя дата + live clock `HH:MM:SS`;
3. уведомления / очки / avatar-profile shortcut.

По ощущению это должны быть встроенные дисплеи электронного органайзера, а не navbar современного SaaS.

## 8.3. Tablet

На tablet сохранить стилистику цельного устройства, но перейти примерно к двум колонкам:

- To‑Do + Focus сверху;
- Today/Profile + Calendar + Stats ниже или рядом;
- не уменьшать focus timer до неудобного размера;
- карточки должны сохранять декоративные рамки и внутренние отступы.

## 8.4. Mobile

На mobile нельзя пытаться втиснуть desktop-панель целиком.

Использовать вертикальный flow:

1. compact header: logo + time + points/avatar;
2. Focus Tool;
3. Today / Profile;
4. To‑Do List;
5. Calendar;

# 11. To‑Do List

To‑Do List — одна из главных функций продукта. Она должна быть быстрее и удобнее декоративных игровых элементов.

## 11.1. Quick Add

Добавление новой задачи должно занимать минимум действий.

На основном экране всегда должна быть очевидная кнопка:

```text
+ Добавить задачу
```

или compact input.

Минимум для быстрой задачи:

- `title`.

Расширенные поля открываются по необходимости:

- описание;
- дата;
- время;
- приоритет;
- предполагаемая длительность.

Enter должен сохранять задачу, если это не ломает ввод многострочного описания.

## 11.2. Task card

Карточка задачи показывает:

- checkbox / completion control;
- название;
- приоритет;
- дату/время, если заданы;
- estimated time, если задан;
- маленькую кнопку «запустить фокус»;
- overflow menu для edit/delete/reschedule.

Не размещать на карточке 8 постоянно видимых иконок.

Вторичные действия показывать через hover/overflow.

## 11.3. Completion

При клике completion:

1. checkbox плавно подтверждает действие;
2. название коротко меняет состояние;
3. начисляются очки;
4. обновляется efficiency tracker;
5. обновляются daily stats;
6. задача перемещается в Completed или сворачивается согласно UI;
7. появляется короткий ненавязчивый feedback.

Не удалять задачу сразу физически — пользователь должен видеть завершённое состояние и иметь возможность Undo.

## 11.4. Undo и защита от farm очков

Если пользователь:

1. выполнил задачу;
2. получил очки;
3. снял completion;
4. снова отметил ту же задачу;

это не должно бесконечно генерировать новые очки.

Используй reward ledger / уникальный completion reward id.

Для demo достаточно правила:

- один task completion reward на один task lifecycle;
- Undo не создаёт новый reward при повторном completion этой же задачи.

При физическом удалении и создании новой задачи это уже новая сущность.

## 11.5. Приоритеты

Минимум три уровня:

- Low;
- Medium;
- High.

В интерфейсе приоритет должен читаться быстро, но не выглядеть как аварийная сигнализация.

Высокий приоритет может иметь более заметный accent.

## 11.6. Секции / фильтры

Обязательно иметь удобные представления:

- Сегодня;
- Предстоящие;
- Без даты;
- Выполненные.

Допустимо добавить All.

На Today показывать задачи с `scheduledDate === today` плюс при желании отдельный небольшой блок overdue.

## 11.7. Перетаскивание

На desktop разрешить drag‑and‑drop для ручной сортировки задач.

При перетаскивании:

- место вставки должно быть визуально понятно;
- остальные карточки плавно освобождают место;
- порядок сохраняется в state/localStorage.

На touch‑устройствах должен оставаться альтернативный способ изменения порядка/даты без drag‑and‑drop.

## 11.8. Редактирование

Edit открывается в аккуратной modal / drawer / popover карточке.

Поля:

- title;
- description;
- date;
- time;
- priority;
- estimated duration.

Autosave допустим, но пользователь должен видеть понятный feedback сохранения.

## 11.9. Удаление

Удаление задачи не должно происходить случайным кликом.

Использовать confirm или короткий undo‑toast.

# 12. Calendar

Calendar должен быть функционально связан с задачами, а не просто показывать число месяца.

## 12.1. Основной режим

Для demo‑версии обязательно реализовать **месячный календарь**.

Показать:

- текущий месяц;
- кнопки previous / next;
- кнопку «Сегодня»;
- дни недели;
- календарную сетку;
- сегодняшний день;
- выбранный день;
- наличие задач на дате.

## 12.2. Задачи в календаре

На каждой дате:

- показать 1–3 коротких task labels, если места хватает;
- либо dots/count для плотного режима;
- при клике на дату справа/снизу открывается список задач выбранного дня.

## 12.3. Создание из календаря

Клик по пустой области дня или `+` создаёт задачу с заранее выбранной датой.

## 12.4. Перенос задачи

На desktop поддержать перенос задачи на другую дату через drag‑and‑drop, если реализация остаётся стабильной.

Обязательно иметь альтернативу:

```text

```

чтобы функция не зависела исключительно от drag‑and‑drop.

## 12.5. Month navigation

Переход между месяцами не должен сбрасывать выбранную дату или пользовательские данные.

# 13. Focus Tool

Focus Tool — второй ключевой модуль после to‑do.

Это должен быть полноценный focus timer, а не обычный текстовый countdown.

## 13.1. Режимы

Поддержать:

- Focus;
- Short Break;
- Long Break.

Дефолтные настройки:

```text
Focus:       25 min
Short break: 5 min
Long break:  20 min
Long break after: 4 completed focus sessions
```

Пользователь может изменить длительности в настройках focus timer.

Дополнительно дать быстрые presets:

- 25 / 5;
- 50 / 10;
- 90 / 15.

Presets не должны мешать ручной настройке.

## 13.2. Элементы Focus card

Показать:

- режим;
- большой таймер `MM:SS`;
- визуальный progress ring / arc;
- связанную задачу;
- Start;
- Pause;
- Resume;
- Reset;
- Skip mode;
- маленький счётчик завершённых focus sessions;
- настройку звука.

## 13.3. Привязка к задаче

Пользователь может выбрать активную задачу из To‑Do List.

На task card также должна быть кнопка типа:

```text
▶ Фокус
```

Она открывает Focus Tool уже с выбранной задачей.

## 13.4. Корректная работа таймера

Не реализовывать countdown как единственное `remaining--` каждую секунду.

Такой подход начинает дрейфовать и ломается в background tab.

При старте сохранить:

```ts
endsAt = Date.now() + remainingSeconds * 1000
```

Во время работы считать:

```ts
remaining = Math.max(0, Math.ceil((endsAt - Date.now()) / 1000))
```

`setInterval` используется только для перерендера отображения.

## 13.5. Перезагрузка страницы

Если таймер был запущен и пользователь обновил страницу:

- состояние восстанавливается;
- оставшееся время вычисляется относительно `endsAt`;
- если таймер уже должен был закончиться, корректно выполнить completion logic один раз.

Не начислять награду дважды из‑за reload.

## 13.6. Pause

При pause:

- вычислить remaining;
- удалить `endsAt`;
- сохранить `remainingSeconds`;
- status = `paused`.

При Resume создать новый `endsAt`.

## 13.7. Completion focus session

Очки начисляются только если **Focus interval дошёл до 0**.

Если пользователь нажал Reset или Skip до завершения — награды нет.

Break session очков не даёт.

После завершения focus interval:

- создать `FocusSession`;
- начислить points;
- обновить daily focus minutes;
- обновить efficiency;
- увеличить счётчик завершённых focus‑сессий;
- переключить на short или long break согласно настройкам;
- показать приятный, но короткий completion feedback.

## 13.8. Очки за focus session

Использовать формулу, которая работает и с custom duration:

```ts
focusPoints = Math.max(3, Math.round(plannedMinutes * 0.6));
```

Примеры:

- 5 min → 3 points;
- 25 min → 15 points;
- 50 min → 30 points;
- 90 min → 54 points.

Очки начисляются один раз на `FocusSession.id`.

## 13.9. Browser title

Во время активной сессии полезно менять title вкладки:

```text
24:12 • Focus Tool
```

После завершения возвращать обычное название.

## 13.10. Звук

Если включён sound:

- короткий мягкий сигнал окончания;
- без резкого autoplay при загрузке;
- выключатель всегда доступен.

Если пользовательский asset pack содержит audio — использовать его.

# 15. Система очков

Gamification должна поддерживать мотивацию, а не захватывать весь интерфейс.

## 15.1. Task points

За завершение задачи:

```text
Low priority    → 10 points
Medium priority → 15 points
High priority   → 20 points
```

Очки выдаются один раз для task lifecycle.

## 15.2. Focus points

По формуле:

```ts
Math.max(3, Math.round(plannedMinutes * 0.6))
```

## 15.3. Total score

Общий score = сумма `PointEvent.points`.

Не хранить отдельное поле `totalPoints`, если его можно безопасно вычислить из ledger. Если для performance нужен cached total — он должен восстанавливаться из событий.

## 15.4. Daily score

Сумма points events для текущего localDate.

Показывать на dashboard компактно.

## 15.5. Feedback при начислении

Пример:

```text
+15
```

может коротко появиться рядом с task card / score indicator и исчезнуть.

Анимация должна быть короткой и не блокировать следующий action.

Не делать полноэкранный modal после каждой задачи.

# 16. Daily Efficiency Tracker

Нужен понятный дневной показатель эффективности.

Он не должен имитировать научно точную оценку человека. Это просто мотивационный progress score приложения.

## 16.1. Метрики

Использовать:

- выполненные задачи на сегодня;
- общее количество задач на сегодня;
- focus minutes за сегодня;
- daily focus goal.

## 16.2. Формула

```ts
taskProgress = scheduledTodayCount > 0
  ? completedTodayCount / scheduledTodayCount
  : 0;

focusProgress = Math.min(focusMinutesToday / dailyFocusGoalMinutes, 1);
```

Если есть и задачи, и focus activity:

```ts
efficiency = Math.round(
  (taskProgress * 0.65 + focusProgress * 0.35) * 100
);
```

Если задач на сегодня нет, но focus был:

```ts
efficiency = Math.round(focusProgress * 100);
```

Если focus не было, но есть задачи:

```ts
efficiency = Math.round(taskProgress * 100);
```

Значение ограничено `0..100`.

## 16.3. UI

Показать:

- ring / bar `0–100%`;
- completed tasks;
- focus minutes;
- points today.

Пример:

```text
Эффективность сегодня
72%

4 / 6 задач
75 мин фокуса
+84 очка
```

Не использовать агрессивные красные предупреждения при низком percentage.

Состояние 0% должно ощущаться как «день только начинается», а не как провал.

# 17. Milestone: три выполненные задачи

Условие:

```ts

```

и


На следующий день milestone снова доступен.

## 17.1. Presentation

Лучший формат:

- красивый toast / small celebration card;
- 1 короткая иллюстрация/asset, если есть подходящий;

- можно закрыть вручную.

Не перекрывать пользователю весь экран на длительное время.

При `prefers-reduced-motion: reduce` particles и масштабные движения отключить.

# 19. Demo Reset

Пока приложение находится в demo‑режиме, должна быть кнопка:

```text
Сбросить
```

Лучшее место:

- Settings/Profile;
- можно дополнительно сделать небольшую demo‑метку.

## 19.1. Поведение

Кнопка reset:

1. открывает confirm dialog;
2. ясно сообщает, что будут удалены задачи, профиль, очки, focus history и записи demo;
3. при подтверждении удаляет только ключи Focus Tool;
4. восстанавливает default state;
5. UI моментально синхронизируется без ручного refresh.

Текст confirm, например:

```text
Сбросить демо‑данные?
Все задачи, очки, focus‑сессии и записи Focus Tool будут удалены с этого устройства.
```

Кнопки:

- Отмена;
- Сбросить.

Destructive action визуально отличать, но без чрезмерно агрессивного дизайна.

# 20. Дизайн-направление — 90s Magical Girl Digital Organizer

Это **обязательное** визуальное направление проекта на основе загруженного референса.

## 20.1. Характер

Ключевые слова:

- 90s magical girl;
- kawaii digital organizer;
- pastel electronic diary;
- cute productivity;
- retro-futuristic pocket planner;
- dreamy;
- soft;
- tactile plastic UI;
- feminine but functional;
- nostalgic without looking obsolete.

Интерфейс должен вызывать ощущение: **«это мой красивый персональный электронный органайзер, который хочется открыть утром и держать рядом весь день»**.

Нельзя уходить в:

- corporate SaaS;
- Notion clone;
- dark dashboard;
- cyberpunk;
- glassmorphism;
- кислотный Y2K;
- тяжёлый skeuomorphism;
- слишком детскую игрушечность;
- визуальный шум из десятков случайных kawaii-стикеров.

## 20.2. Основная палитра

Базовая палитра должна быть очень светлой и пастельной. Точные значения можно немного скорректировать после появления asset sheet, но визуальная температура должна сохраняться.

Стартовые CSS tokens:

```css
--bg-page: #f7dfe5;
--bg-shell: #f8d5df;
--surface-main: #fff7ee;
--surface-soft: #fff1ea;
--surface-pink: #fbd5df;
--surface-pink-strong: #f5aec4;
--surface-lilac: #eadcf5;
--surface-peach: #f8dfcf;

--border-soft: #d9aebb;
--border-lilac: #bda7c8;
--line-muted: #ead6d8;

--text-main: #5a5452;
--text-muted: #8d7f7e;
--text-pink: #d56f98;
--text-lilac: #8f75a8;

--accent-pink: #ee8eae;
--accent-pink-hover: #e57fa2;
--accent-lilac: #b89bd4;
--accent-yellow: #f1cf72;
--accent-mint: #acd8c1;

```

Не воспринимать hex как immutable design system. Если реальные assets требуют чуть более холодной/тёплой гаммы — подстроить tokens под них.

Обязательные требования:

- фон не должен быть чисто белым;
- основной текст не должен быть чисто чёрным;
- розовый не должен становиться neon/magenta;
- контраст текста обязан оставаться достаточным для чтения.

## 20.3. Панели и карточки

Карточки должны напоминать панели физического электронного устройства:

- ivory / cream fill;
- тонкий pink/lilac outline;
- мягкая внешняя тень;
- очень лёгкая внутренняя тень или highlight;
- иногда двойная рамка;
- скругления средней величины;
- декоративные corner details допустимы;
- ощущение слегка выпуклого пластика.

Рекомендуемые радиусы:

```text
small controls: 10–14px
small panels:   14–18px
cards:          16–22px
large panels:   20–28px
pill/chips:     999px
focus circle:   50%
```

Рекомендуемая тень:

```css
box-shadow:
  0 4px 10px rgba(121, 79, 91, 0.10),
  inset 0 1px 0 rgba(255, 255, 255, 0.75);
```

Не использовать тяжёлую современную shadow уровня modal/card SaaS.

## 20.4. Focus Timer — визуальный центр

Focus Timer должен быть самым выразительным элементом экрана.

Сделать большую круглую/овальную timer-console:

- внешний pastel корпус;
- одна или несколько декоративных рамок;
- внутри кремовый / слегка зеленоватый LCD-like display;
- крупное цифровое время;
- подпись `FOCUS TIME` / выбранная задача;
- небольшая magical-girl эмблема сверху;
- 2–4 маленьких декоративных элемента вокруг корпуса из asset sheet;
- мягкое свечение/пульсация только во время running state.

У Focus Tool должны быть заметные, удобные controls:

- основной `START` / `RESUME` — большая розовая pill-кнопка;
- `PAUSE`;
- `RESET`;
- пресеты времени отдельными маленькими кнопками.

Активный preset визуально заполнен pastel pink/lilac, остальные — ivory.

Timer digits:

- `font-variant-numeric: tabular-nums`;
- стабильная ширина цифр;
- никакого layout shift каждую секунду;
- при наличии подходящего пользовательского digital font asset использовать его;
- иначе использовать максимально читаемый rounded/system font без подключения сомнительных внешних шрифтов.

## 20.5. To-Do panel

Левая большая панель из референса становится **MY TASKS / TO-DO**.

Она должна выглядеть как страница электронного ежедневника:

- заголовок pastel pink;
- небольшая тематическая иконка;
- строки задач разделены тонкими линиями;
- checkbox / status icon слева;
- название задачи по центру;
- справа небольшой priority / time / points indicator;
- completed задача становится мягче по контрасту и получает strike-through;
- не перечёркивать весь row агрессивно;
- quick-add расположен сверху или снизу панели и должен быть доступен одним действием.

У задач допустимы маленькие category icons, но только из единой системы или asset sheet.

## 20.6. Today / Profile panel

Правая верхняя карточка должна визуально напоминать блок `TODAY` из референса.

Внутри:

- `How are you feeling?` / русская локализованная версия;
- 5 mood-кнопок;
- выбранное настроение подсвечивается;
- поле `О чём я сегодня думаю`;
- декоративная иллюстрация в нижнем углу, если подходящий asset есть;
- autosave без отдельной тяжёлой кнопки Save.

Mood buttons могут быть круглыми pastel-face/custom-icon controls. Если asset sheet содержит готовые expressions — использовать их. Иначе сделать аккуратные line-icons, не emoji системного шрифта.

## 20.7. Calendar

Календарь — компактная отдельная cream panel с pastel header.

- текущий день выделен розовым filled-circle;
- дни с задачами получают маленькую точку / star marker;
- завершённый продуктивный день может получать tiny sparkle;
- selected day должен быть визуально отличим от today;
- навигация месяца — очень компактные arrow controls;
- не использовать тяжёлый сторонний календарный виджет с чуждым стилем.

## 20.8. Daily Efficiency / Stats

Нижняя панель должна стилистически наследовать `MONTHLY STATS` из референса, но показывать полезную продуктивность.

Пример состава:

```text
Completed       Focus sessions       Focus min       Points
5 / 7           3                    75              680
```

Дополнительно показать:

- efficiency percentage;
- небольшой progress bar / segmented meter;
- achievement badge справа, если он разблокирован.

Stats не должны превращаться в полноценную BI-dashboard аналитику.

## 20.9. Rewards / Achievement card

После milestone или особенно хорошего дня показывать небольшую pastel-card справа снизу:

- star/sparkle icon;
- короткое сообщение;
- новый badge / points feedback;
- мягкий entrance animation.

Если пользователь выполнил 3 задачи, здесь же может появиться одно из 30 поощрений.

## 20.10. Кнопки

Кнопки должны напоминать физические controls электронного органайзера:

- rounded rectangle / pill;
- лёгкая верхняя подсветка;
- subtle shadow;
- pressed state с `translateY(1px)` и уменьшенной тенью;
- hover делает поверхность чуть насыщеннее, а не резко меняет цвет;
- active state считывается без анимационного шума.

Primary:

- pastel pink fill;
- светлый текст или контрастный muted-plum text в зависимости от контраста.

Secondary:

- cream fill;
- pink/lilac border.

Danger (`Demo Reset`, delete):

- не делать ярко-красной;
- использовать muted dusty rose;
- destructive смысл подтверждается иконкой и confirm dialog.

## 20.11. Иконки и декоративные элементы

Приоритет:

1. пользовательский asset sheet;
2. custom SVG/CSS decorations;
3. Lucide для утилитарных действий.

Lucide подходит для:

- add;
- edit;
- delete;
- pause/play/reset;
- calendar arrows;
- archive;
- settings.

Magical decorations лучше брать из asset sheet:

- stars;
- sparkles;
- flames;
- moons;
- wings;
- badges;
- mascot elements;
- avatar frames.

Не смешивать пять разных icon styles.

## 20.12. Типографика

Общий UI должен быть округлым, дружелюбным и очень читаемым.

Предпочтительная иерархия:

- brand: rounded display lettering;
- section headings: uppercase / small caps pastel-pink, `12–14px`, повышенная читаемость;
- body: `14–16px`;
- metadata: `11–13px`;
- live clock: `18–24px`, tabular nums;
- focus timer: `48–72px` desktop;
- stats values: `22–30px`.

Можно использовать `Nunito`, `Quicksand`, `M PLUS Rounded 1c` или близкий rounded font **только если подключение внешнего шрифта допустимо и стабильно**. Иначе использовать качественный rounded/system fallback.

Не использовать декоративный шрифт для длинного текста задач.

## 20.13. Детали корпуса

Для усиления сходства с электронным органайзером допустимы:

- очень тонкая рамка всего приложения;
- маленькие декоративные «винты» / corner dots;
- двойная линия по краю shell;
- tiny sparkle в углах;
- визуальные стыки между панелями;
- небольшие recessed areas под controls.

Но это должно быть сделано через CSS и ассеты аккуратно. Не рисовать фальшивый 3D-пластик с тяжёлыми bevel-эффектами.

## 20.14. Background

Основной фон страницы — мягкий pastel pink / blush.

Сам organizer может лежать на чуть отличающемся фоне и иметь:

- max-width;
- centered placement;
- мягкую общую тень;
- небольшую внутреннюю border-line.

На больших desktop-экранах вокруг organizer допустимо оставлять свободное пространство, чтобы интерфейс ощущался как отдельный объект/device.

## 20.15. Визуальная плотность

Референс довольно плотный, но аккуратный. Повторить именно этот баланс:

- много информации видно сразу;
- каждая зона имеет свой контейнер;
- отступы небольшие, но не тесные;
- минимум пустых гигантских областей;
- главные controls крупнее вспомогательных;
- декоративные элементы занимают не более примерно 10–15% визуального внимания.

# 21. Motion / Animations

Плавность — важная часть продукта, но анимация должна помогать интерфейсу, а не отвлекать от задач.

## 21.1. Рекомендуемые времена

```text
button press / checkbox:  90–140 ms
hover state:             120–180 ms
chip/filter:             140–200 ms
task insert/reorder:     160–240 ms
popover/dropdown:        160–220 ms
modal/drawer enter:      220–300 ms
modal/drawer exit:       160–240 ms
reward celebration:     400–800 ms, но не блокирующая
```

Не растягивать обычные UI transitions до 500–1000 ms.

## 21.2. Easing

Использовать natural easing:

```css
cubic-bezier(0.2, 0.8, 0.2, 1)
```

или эквивалентный spring без сильного bounce.

## 21.3. Что анимировать

Хорошие места:

- checkbox completion;
- task insertion/removal;
- drag reorder;
- score increment;
- tab/view transition;
- opening profile/calendar drawer;
- focus progress ring;
- milestone toast;
- mood selection;
- button press feedback.

Не делать:

- постоянно движущиеся decorative backgrounds;
- бесконечный floating каждого элемента;
- чрезмерный parallax;
- мигающие score badges;
- bouncing controls в idle state.

## 21.4. Reduced motion

Обязательно учитывать:

```css
@media (prefers-reduced-motion: reduce) {
  /* suppress non-essential motion */
}
```

Для JS/Motion animations тоже проверять системную настройку.

При reduced motion:

- убрать confetti/particle travel;
- убрать большие slide/scale transitions;
- оставить мгновенные state changes и opacity feedback.

# 33. Состояния Focus Tool

Явно продумать state machine.

## Idle focus

- timer показывает configured duration;
- Start active;
- Pause disabled;
- Reset disabled или возвращает default.

## Running

- Start hidden/disabled;
- Pause active;
- Reset active;
- task picker можно заблокировать или потребовать reset перед сменой задачи.

## Paused

- Resume active;
- Reset active.

## Completed

Completion handler выполняется один раз и переводит приложение в break mode.

Не оставлять transient `completed` state, из которого reload может повторно начислить награду.

# 34. Связь To‑Do и Focus

Эти модули должны ощущаться частью одного продукта.

Сценарий:

1. пользователь создаёт задачу;
2. нажимает `Фокус` на карточке;
3. Focus Tool открывается с названием задачи;
4. запускается timer;
5. после завершения сессия записывается в историю;
6. focus minutes добавляются к дневной статистике;
7. задача **не завершается автоматически**, потому что одна задача может потребовать несколько focus sessions;
8. пользователь сам отмечает задачу Completed.

В task editor можно показывать суммарные focus minutes по этой задаче, если это не перегружает UI.

# 38. Сохранение профиля и check‑in

Имя — глобальное.

Mood и thought — дневные.

Пример:

```ts
checkIns: {
  '2026-09-03': {
    date: '2026-09-03',
    mood: 'good',
    thought: 'Сегодня хочу закончить главное до вечера.',
    updatedAt: 1788460000000,
  }
}
```

При открытии Profile сегодня загружать `checkIns[today]`.

# 39. UX‑приоритеты

При любых спорных решениях соблюдать порядок:

1. Быстро понять, что делать.
2. Быстро добавить задачу.
3. Быстро отметить completion.
4. Быстро запустить focus.
5. Не потерять данные.
6. Понятно видеть состояние дня.
7. Только потом декоративная геймификация.

Если декоративный asset мешает task readability — task readability важнее.

Если animation мешает скорости — сократить animation.

Если новая фича усложняет demo и не относится к ключевым требованиям — не добавлять её.

- 1–2 tasks → нет milestone;

- countdown from endsAt;
- pause;
- resume;
- reload restore;
- completion один раз;
- reset не выдаёт очки;
- break не выдаёт очки.

## 41.5. Storage

Проверить:

- default state;
- save/load;
- malformed JSON;
- reset только app namespace.

# 46. Исследовательская основа решений

Эта спецификация учитывает практики современных productivity‑продуктов и UX‑рекомендации:

- Todoist: Today/Upcoming, priorities, dates, task duration, calendar layout, time blocking, productivity/Karma patterns.
- Sunsama: daily planning, time estimates, planned vs actual time, focus mode, tasks + calendar/timeboxing.
- Habitica: мягкая геймификация выполнения реальных задач через награды.
- Pomodoro workflow: классический 25/5 и длинный перерыв после серии focus intervals, при этом длительность должна оставаться настраиваемой.
- Nielsen Norman Group: UI motion должно прежде всего давать feedback и объяснять state changes; обычные интерфейсные анимации должны быть короткими и ненавязчивыми.
- MDN Web Storage: `localStorage` ограничен квотой и может выбрасывать `QuotaExceededError`, поэтому нужен safe storage layer.
- W3C/WCAG: учитывать `prefers-reduced-motion` для несущественных motion effects.

# 47. Итоговый приоритет продукта

**Focus Tool должен быть не «игрой с задачами», а очень удобным инструментом продуктивности, которому геймификация добавляет приятную обратную связь.**

Главное ощущение:

> Открыл → сразу понял день → быстро добавил задачи → выбрал одну → включил focus → закончил → получил спокойное подтверждение прогресса → видишь, что день движется.

Дизайн и пользовательские assets должны сделать этот цикл приятным и визуально узнаваемым, но никогда не мешать самому циклу.
